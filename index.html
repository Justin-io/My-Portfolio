AUTONOMOUS AI / ANALYTICS ENGINEERING

Autonomous AI Data Scientist

A controlled analysis workflow that turns business questions into evidence-linked SQL, statistical investigation and reviewable reports. The system is designed to refuse unsupported questions rather than invent missing data.

Engineering breakdown Problem · architecture · evidence · limits
Problem
Text-to-SQL systems can select the wrong grain, create join fanout, mutate data or produce plausible explanations unsupported by the warehouse.
System design
A 21-state bounded workflow with a canonical semantic layer, SQL AST validation, hypothesis testing, an independent critic and human review checkpoints.
Architecture
Python, FastAPI, DuckDB and a React + TypeScript analyst workspace. SHA-256 dataset references bind generated claims to the data used for analysis.
Repository evidence
The committed TEST_MATRIX.md records 46 passing tests across 10 suites, covering warehouse generation, semantic validation, SQL safety, statistics, causal checks, evidence verification and API flows.
Scope limit
The bundled warehouse and scenarios are synthetic. Passing tests verify implemented code paths; they do not establish accuracy on external customer data or production business outcomes.

RETRIEVAL SYSTEMS / EMPIRICAL EVALUATION

RAG Evaluation Platform

A reproducible harness for comparing retrieval-augmented generation architectures under a shared evaluation protocol, with retrieval, grounding, robustness, latency and cost measurements.

Engineering breakdown Problem · architecture · evidence · limits
Problem
RAG demos often report anecdotal quality without comparable datasets, retrieval metrics, adversarial cases or operational cost measurements.
Architectures
Naive, hybrid BM25+dense with RRF, reranked, query-rewriting/HyDE, GraphRAG and agentic RAG, executed through a common harness.
Evaluation
Precision@k, Recall@k, MRR, NDCG@k, faithfulness, citation precision/recall, adversarial robustness, latency percentiles and token/cost models, with paired statistical comparisons.
Repository evidence
The committed TEST_MATRIX.md records 34 passing tests across 9 suites, covering ingestion, retrieval stores, six architectures, metrics, robustness, statistics, storage and API execution.
Scope limit
The included challenge sets are synthetic. Results from this harness are dataset- and configuration-dependent, not a universal ranking of RAG architectures or proof of customer-corpus performance.

GRAPH ML / FINANCIAL RISK RESEARCH

FraudShield AI — Real-Time Graph Fraud Platform

A streaming fraud-research platform that models relationships among users, cards, devices, IPs, merchants and addresses, then compares tabular, anomaly-detection and graph-learning approaches.

Engineering breakdown Problem · architecture · evidence · limits
Problem
Isolated transaction features can miss coordinated patterns that emerge across linked entities and change over time.
Architecture
A temporal heterogeneous graph, streaming feature windows, point-in-time state, drift monitoring and a FastAPI + React investigation interface.
Model comparison
Eight model families from logistic/XGBoost baselines and anomaly detectors to GCN, GraphSAGE, GAT and Temporal GNN, compared with leakage-aware temporal evaluation.
Repository evidence
The README reports 24/24 tests passing and approximately 12.8 ms P99 typical latency for its stated local workload. Treat that latency as a repository-reported synthetic benchmark, not a financial-network SLA.
Scope limit
The simulator and injected fraud patterns are synthetic. This is not connected to a bank or live payment processor and has not established production fraud-detection performance.

ABOUT THE BUILDER

Curiosity across software and physical systems

A practical engineering approach: understand the system, make assumptions explicit, build a testable implementation and show where the evidence stops.

I am Hari Nandan K, an independent builder working across applied AI, data systems, defensive security, environmental intelligence, digital signal processing and embedded engineering. My repositories range from autonomous analysis and retrieval evaluation to geospatial research, audio DSP and hardware design.

I care about the engineering beneath the interface: data contracts, state machines, SQL safety, evaluation methodology, provenance, access control, latency budgets and how a system behaves when its assumptions fail.

I also build client-facing engineering and estimation tooling through Build with Hari, alongside education and community products through the HOPE initiative. The goal is to make technical work and learning more practical through reviewable product workflows, interactive documents, coding tools and AI-assisted experiences.

I distinguish a passing test suite from field validation, synthetic data from measured data, and a digital hardware design from a fabricated board. That distinction is part of the engineering, not a footnote.

Data provenance
